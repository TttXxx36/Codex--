## 理解与边界

测速矩阵必须消除任何由 RTT 乘数推导的伪造 TTFT；流式探测只报告真实首个非空 SSE 分块阶段时间，非流式响应只报告真实 HTTP 往返耗时并将 TTFT 留空。所有 2xx 才能进入成功/评分集合，3xx 必须保留原始状态并给出更新供应商目标 URL 的指引；不改凭据、IPC 以外的协议、无关 UI 或提交/推送状态。

## 调研与复用

- 官方 Fetch/Streams 资料确认 `Response.body` 是可按 chunk 读取的 `ReadableStream`；Fetch 标准定义 301/302/303/307/308 为 redirect status，`Response.redirected` 只能在跟随发生后观察结果，因此测速 client 使用 `redirect: none`，不把最终 200 误判为健康端点。
- 复用既有 `test_relay_profile` 命令、`reqwest` 的 `stream` feature、`futures-util::StreamExt`、现有 speed matrix/Provider Doctor/diagnostic 契约；没有新增依赖。
- 冲突裁决：架构师审查边界与真实数据红线优先于“所有供应商必须兼容”的隐含假设；测速请求显式开启 stream，流式不支持时不伪造 TTFT，兼容降级策略留给架构师确认。
